# SentinelCore — SIEM на C++ (этап 6: расследование)

Сервер принимает логи, разбирает их, ищет атаки по правилам, хранит события на диске и отдаёт всё по HTTP API.
Агент на защищаемом сервере сам находит логи и надёжно доставляет их по HTTPS.
Веб-панель (React) открывается прямо с сервера: обзор, алерты, поиск событий, правила, подключение серверов и живая лента.
О важных атаках SIEM сообщает в Telegram, на почту или в Slack/Discord, а атакующие адреса блокирует
в брандмауэре защищаемых серверов (nftables, iptables, pf, брандмауэр Windows или nginx).
Правила обнаружения можно писать и проверять прямо в панели: на строках логов и на уже сохранённых событиях.
Для расследования: страна и сеть каждого адреса, чёрные списки, **инциденты** (алерты одной атаки в одной карточке
с ответственным и заметками), **выгрузка** в CSV/JSON и **отчёт за период** — для печати в PDF и еженедельным письмом.
**Весь код свой**: стандартная библиотека C++20 и функции операционной системы. Свой HTTP-сервер и клиент, свой JSON,
свой YAML, свой движок регулярных выражений, своё сжатие и своё хранилище. Единственное исключение — **шифрование
через системный OpenSSL** (`src/net/tls.cpp`); без него проект тоже собирается, просто без HTTPS.

## Что внутри

```
[агент] ──HTTPS──▶ [приём и разбор] ──очередь──▶ [обнаружение атак] ──по порядку──▶ [запись на диск]
                (N потоков)                   (потоки по IP + общий)          (сжатие в N потоках)
                                                                                    │
панель / curl ◀──────────────────────── HTTP API (поиск, алерты, статистика) ◀──────┘
панель ◀── WebSocket /ws/live (раз в секунду: сколько событий, последние события, новые алерты)

новый алерт ──▶ уведомления (Telegram / почта / webhook)
            └──▶ список блокировок ──▶ агенты забирают его раз в 15 с ──▶ брандмауэр сервера
```

| Папка | Что делает |
|---|---|
| `src/core` | строки, время, JSON, YAML, SHA-256, IP-адреса и подсети, логгер |
| `src/regex` | свой движок регулярных выражений: строго линейное время, все шаблоны за один проход |
| `src/parse` | разбор nginx/apache, syslog (SSH, sudo, su, брандмауэр), JSON, key=value |
| `src/detect` | правила и движок обнаружения: совпадение, порог, цепочка событий; деление правил между потоками |
| `src/store` | хранилище: сегменты, блоки со сжатием (в нескольких потоках), CRC, bloom-фильтры, восстановление после сбоя |
| `src/net` | HTTP/1.1 сервер (epoll / poll / WSAPoll) и клиент, SMTP-клиент; `tls.cpp` — HTTPS через OpenSSL |
| `src/enrich` | своя база стран и сетей по IP, чёрные списки адресов (скачивание и обновление), обогащение событий |
| `src/server` | конфиг, ключи, токены подключения агентов, конвейер обработки, API, вход в панель, живая лента, раздача панели, уведомления, список блокировок, правка правил, `main` |
| `src/agent` | агент: автопоиск логов, чтение хвоста с позицией, ротации, доставка с повторами, журнал Windows, применение блокировок в брандмауэре |
| `web/` | панель на React + TypeScript (из зависимостей только React; графики, иконки, маршруты — свои) |
| `rules/` | 16 правил обнаружения, у каждого встроенные примеры «должно сработать / не должно» |
| `tests/` | 108 тестов (свой мини-фреймворк) |
| `packaging/macos/` | приложение для Mac (значок в строке меню), сборка `.dmg` |
| `Dockerfile`, `docker/` | образ и `docker-compose.yml` |
| `tools/bench.cpp` | замер скорости |

## Установка

Готовые сборки — на странице [Releases](https://github.com/KishoHiga/SIEM/releases):

**Приложение для Mac** (`SentinelCore-<версия>-macOS.dmg`, Apple Silicon и Intel, macOS 12+): перетащите в «Программы»
и запустите. В строке меню появится значок щита, а панель откроется в браузере уже под администратором.
Приложение не подписано платным сертификатом Apple, поэтому первый запуск нужно разрешить:
macOS 15+ — Системные настройки → Конфиденциальность и безопасность → «Всё равно открыть»;
macOS 12–14 — правый щелчок → «Открыть». Данные — `~/Library/Application Support/SentinelCore`.

**Docker** (amd64 и arm64): скачайте `docker-compose.yml` из релиза (он же лежит в `docker/`) и выполните
```bash
docker compose up -d
docker compose logs sentinel     # ключ администратора
```
Панель — http://localhost:8080. Данные — в томе `sentinel-data`. Обновление: `docker compose pull && docker compose up -d`.

Переменные окружения (для Docker и не только):

| Переменная | Что делает |
|---|---|
| `SENTINEL_ADMIN_KEY` | ключ администратора, который создаётся при первом запуске (20+ символов). Без неё сервер придумает ключ сам и покажет его |
| `SENTINEL_LISTEN` | где слушать, `host:port` (вместо `listen` в конфиге) |
| `SENTINEL_PUBLIC_URL` | адрес, по которому агенты достучатся до сервера (попадает в готовую команду подключения) |
| `SENTINEL_TLS=on` | HTTPS с самоподписанным сертификатом в `<data_dir>/tls` (создаётся один раз) |
| `SENTINEL_TLS_NAMES` | имена и адреса для этого сертификата через запятую |
| `SENTINEL_WEB_DIR` | где лежит собранная панель (вместо `web_dir`) |

Проверка, что сервер жив (её использует Docker): `sentinel-server healthcheck -c sentinel.yaml`.

## Сборка из исходников

Нужны компилятор C++20, CMake и (для HTTPS) OpenSSL.

**macOS**
```bash
xcode-select --install        # компилятор (один раз)
brew install cmake openssl@3  # cmake и OpenSSL (находится автоматически)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

**Linux (Ubuntu/Debian)**
```bash
sudo apt install build-essential cmake libssl-dev
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

**Windows** — Visual Studio 2022 (компонент «Разработка классических приложений на C++») и OpenSSL
(например, `vcpkg install openssl:x64-windows`):
```bat
cmake -S . -B build -DCMAKE_TOOLCHAIN_FILE=C:/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build build --config Release
```
Если OpenSSL не найден, CMake предупредит и соберёт всё без HTTPS.

**Панель** (нужен Node.js 20+, только для сборки — на сервере Node не нужен):
```bash
cd web
npm install
npm run build        # результат в web/dist, сервер раздаёт его сам (настройка web_dir)
```

Проверка, что всё работает:
```bash
./build/sentinel-tests                      # 108 тестов
./build/sentinel-server test-rules          # правила на своих примерах
./build/sentinel-bench --rules rules        # замер скорости
```

## Запуск

```bash
cp sentinel.example.yaml sentinel.yaml
./build/sentinel-server run -c sentinel.yaml
```

При первом запуске сервер создаёт **ключ администратора** и показывает его один раз. Сохраните его.
Сам ключ нигде не хранится, на диске лежит только его хеш (`data/keys.yaml`).

Ключ для сайта или агента, который может только **отправлять** логи:
```bash
./build/sentinel-server keygen --name web-01 --role ingest
```
Роли: `ingest` (только отправка), `read` (только чтение), `analyst` (чтение и смена статуса алертов), `admin` (всё).
Работающий сервер подхватывает новые ключи сам, в течение 2 секунд.

## Панель

Откройте в браузере адрес сервера, например `http://127.0.0.1:8080/` (или `https://...`, если включён TLS),
и войдите по ключу с ролью `read`, `analyst` или `admin`. Ключ агента (`ingest`) в панель не пускает.

| Раздел | Что там |
|---|---|
| Обзор | события в секунду, график событий и алертов, алерты по важности, самые активные IP и источники, хранилище, живая лента |
| Алерты | фильтры по статусу, важности, IP и правилу; «В работу» / «Решён» прямо в списке; новые алерты появляются сами |
| Алерт | что сработало, IP и пользователь (со ссылками на все их события), связанные события целиком, смена статуса, кнопка **«Заблокировать IP»** (или отметка, что адрес уже заблокирован) |
| События | поиск по тексту, фильтры по любому полю, период, «Показать ещё»; клик по строке — карточка события. Адрес страницы можно отправить коллеге — откроется тот же поиск |
| Реагирование | заблокированные адреса (кто, за что, до какого времени), «Заблокировать адрес», «Разблокировать», настройки автоблокировки, каналы уведомлений и кнопка «Тест» |
| Правила | все правила, сколько алертов каждое дало за сутки (и сколько из них ложных), включение и выключение одним щелчком, **«Новое правило»** |
| Правило | редактор YAML с подсветкой и проверкой на лету; проверка на строках логов и на уже сохранённых событиях; версии; сохранение, удаление |
| Серверы | подключённые агенты (на связи / нет), состояние брандмауэра на каждом сервере, кнопка **«Подключить сервер»** — панель выдаёт готовую команду для агента |
| Подключить сайт | мастер в 4 шага: на чём сделан сайт → как включить журнал запросов (готовый код для Express, Flask, Django, PHP, WordPress; nginx и Apache — путь к журналу) → команды для агента → ждёт первую строку и показывает «Готово». Подробно: [docs/connect-site.md](docs/connect-site.md) |

Безопасность панели:
- после входа браузер хранит только cookie сессии с флагами `HttpOnly` (скрипты её не видят), `SameSite=Strict`
  и `Secure` (при HTTPS); сессия живёт 12 часов с последнего действия, после удаления ключа сразу перестаёт работать;
- изменяющие запросы из браузера требуют заголовок `X-Requested-With: sentinel` — чужой сайт не сможет
  выполнить действие от вашего имени;
- живая лента принимает только страницы с того же адреса (проверка `Origin`); подключается по одноразовому
  билету на 60 секунд (`POST /api/v1/ws-ticket`), потому что Safari не всегда передаёт cookie в WebSocket;
  при открытии лента сразу показывает последние события из базы;
- страница отдаётся с запретом встраивания и строгой политикой `Content-Security-Policy`.

Разработка панели с автообновлением: запустите сервер, затем
```bash
cd web
SENTINEL_URL=https://127.0.0.1:8443 npm run dev    # откройте http://localhost:5173
```

## HTTPS

```bash
./build/sentinel-server gen-cert -c sentinel.yaml --names siem.example.com,203.0.113.10
```
Команда создаёт сертификат `data/tls/server.crt` и ключ `data/tls/server.key`, а затем выводит **отпечаток**
`sha256:...`. Добавьте в `sentinel.yaml`:
```yaml
listen: 0.0.0.0:8443
public_url: https://siem.example.com:8443
tls:
  cert: ./data/tls/server.crt
  key: ./data/tls/server.key
```
Агенты доверяют серверу по отпечатку (закрепление сертификата): покупать сертификат не нужно, а подменить сервер нельзя.
Если у вас уже есть настоящий сертификат (например, Let's Encrypt), укажите его в `tls:`, и агентам отпечаток не понадобится.

## Подключение защищаемого сервера (агент)

**1. На сервере SIEM** создайте одноразовый токен:
```bash
./build/sentinel-server enroll-token -c sentinel.yaml          # --ttl 24h --uses 1 по умолчанию
```
Команда выведет готовую команду для агента вместе с токеном и отпечатком.

**2. На сервере с сайтом** (скопируйте туда `sentinel-agent`):
```bash
sentinel-agent discover                     # покажет, какие логи найдены
sentinel-agent enroll --server https://siem.example.com:8443 --token sne_... --pin sha256:...
sentinel-agent test                         # проверка связи
sentinel-agent add /var/www/shop/logs/access.log --name shop   # журнал своего сайта
sentinel-agent service install              # работать в фоне (launchd / systemd / служба Windows)
```
Вместо `service install` можно запустить в открытом окне: `sentinel-agent run`.
Как включить журнал запросов в Express, Flask, Django, PHP и WordPress — в [docs/connect-site.md](docs/connect-site.md)
(или мастер «Подключить сайт» в панели).

| Команда агента | Что делает |
|---|---|
| `add ФАЙЛ [--name ИМЯ] [--format …] [--from-beginning]` | добавить файл в `agent.yaml` (комментарии сохраняются); формат определяется по последним строкам; работающий агент подхватывает изменения `agent.yaml` за 2 секунды без перезапуска |
| `remove ФАЙЛ`, `sources` | убрать файл; что читается сейчас |
| `service install \| uninstall \| status \| print` | фоновая служба: macOS — launchd (`~/Library/LaunchAgents`, под `sudo` — `/Library/LaunchDaemons`), Linux — systemd (`sudo`), Windows — служба `SentinelAgent` (от администратора) |

Без `-c` агент берёт `./agent.yaml`, а если его нет — `agent.yaml` рядом с программой. Второй агент с теми же
настройками не запустится (иначе строки задвоились бы).
`enroll` получает у сервера **личный ключ агента** (роль `ingest`: только отправка) и записывает `agent.yaml`.
Токен одноразовый и живёт 24 часа. Подключённые агенты видны в `GET /api/v1/agents`.

**Что агент находит сам:**

| Система | Источники |
|---|---|
| Linux | nginx и Apache (access-логи), `/var/log/auth.log` или `/var/log/secure` (SSH, sudo, su), `/var/log/syslog` или `/var/log/messages` (включая брандмауэр UFW/iptables), логи Docker-контейнеров; если `auth.log` нет — journald |
| macOS | nginx из Homebrew, Apache, системный журнал (`log stream`: sshd, sudo, su) |
| Windows | журнал безопасности: входы и неудачные входы, блокировки, создание и удаление пользователей, добавление в группы, очистка журнала |

Свои источники можно добавить в `agent.yaml` в раздел `sources:` (маски `*` поддерживаются), а лишние убрать через `exclude:`.

**Надёжность доставки.** Позиция чтения файла сдвигается **только после того, как сервер подтвердил приём**.
Если сервер недоступен, агент ждёт (1 → 2 → 4 … 60 с) и повторяет отправку: буфером служат сами файлы логов.
Позиции сохраняются в `state/state.json`, поэтому после перезапуска агент продолжает с того же места без дублей.
Ротацию (logrotate) агент замечает: старый файл дочитывает, а новый читает с начала.
Для логов без часового пояса (syslog) агент сообщает серверу смещение своего пояса.

## Уведомления

В `sentinel.yaml` раздел `notify:` (полный пример — в `sentinel.example.yaml`):
```yaml
notify:
  min_severity: high          # присылать алерты от этого уровня
  telegram:
    bot_token: '123456:ABC...'
    chat_id: '-1001234567890'
  email:
    smtp: smtp.yandex.ru:465
    username: siem@example.com
    password: 'пароль приложения'
    to: ['admin@example.com']
  webhook:
    url: https://hooks.slack.com/services/...
    format: slack             # json | slack | discord
```
- Одна и та же атака (правило + IP) не присылается чаще раза в `cooldown` (10 минут).
- Если за 5 секунд набралось больше 3 алертов, вместо пачки сообщений приходит **одна сводка**.
- Неудачная отправка повторяется 3 раза. Счётчики и последняя ошибка каждого канала видны в панели.
- Почта поддерживает STARTTLS (порт 587) и SSL (465), вход AUTH PLAIN / LOGIN. Telegram и webhook работают по HTTPS
  с проверкой сертификата.
- Проверить настройки можно кнопкой **«Тест»** в разделе «Реагирование» (только администратор).
- `mode: incidents` — писать не про каждый алерт, а только когда **появился новый инцидент** или **инцидент стал
  серьёзнее** (см. ниже). Сообщений становится в разы меньше, а ссылка ведёт сразу в карточку инцидента.

## Блокировка атакующих адресов

**Как это работает.** SIEM ведёт общий список заблокированных адресов (`data/blocks.json`). Адрес попадает туда:
- **автоматически**: алерт уровня `critical` (настраивается) от внешнего IP, адрес блокируется на 1 час;
- **вручную**: в панели, кнопки «Заблокировать адрес» и «Заблокировать IP» в карточке алерта (роль analyst или admin).

Агенты раз в 15 секунд забирают список и применяют его в брандмауэре своего сервера.
Когда срок блокировки истекает, адрес сам уходит из списка и из брандмауэров.

**Защита от ошибок:**
- никогда не блокируются localhost, служебные адреса и слишком широкие сети (шире /8 для IPv4, шире /16 для IPv6);
- внутренние сети (10.x, 172.16–31.x, 192.168.x, fc00::/7) не блокируются, пока не включён `block_private`;
- адреса из `allowlist` не блокируются ни автоматически, ни вручную; на агенте есть свой `allowlist`;
- агент никогда не блокирует адрес самого SIEM, иначе он потерял бы связь с сервером;
- автоматически блокируется не больше `max_per_minute` новых адресов в минуту.

Настройка на сервере SIEM (`sentinel.yaml`):
```yaml
response:
  auto_block:
    enabled: true
    min_severity: critical
    duration: 1h              # 0 — навсегда
  allowlist: ['203.0.113.10']
```

**Включение на защищаемом сервере** — одна строка в `agent.yaml`:
```yaml
firewall: auto
```
`auto` выбирает: nftables или iptables на Linux, pf на macOS, брандмауэр Windows на Windows.
Для блокировки в брандмауэре агент должен работать от root (администратора), например как служба.

| Режим | Что делает агент |
|---|---|
| `nftables` | своя таблица `inet sentinel` с наборами адресов; пакеты отбрасываются до маршрутизации, поэтому блокировка работает и для портов Docker; список заменяется одной атомарной командой `nft -f` |
| `iptables` | своя цепочка `SENTINEL` в таблице `raw` (IPv4 и IPv6), замена через `iptables-restore` |
| `pf` | якорь `com.apple/sentinel` со своей таблицей адресов (macOS) |
| `windows` | правила «SentinelCore Block» в брандмауэре Windows |
| `nginx` | файл `deny ...;` (по умолчанию `/etc/nginx/conf.d/sentinel-blocklist.conf`), затем `nginx -t` и мягкая перезагрузка; если проверка не прошла, старый файл возвращается. Root на брандмауэр не нужен |
| `command` | своя программа: агент записывает список в файл и запускает `команда <файл>` |

Расширенная настройка:
```yaml
firewall:
  mode: nginx
  nginx_file: /etc/nginx/conf.d/sentinel-blocklist.conf
  allowlist: ['10.0.0.0/8']   # не блокировать на этом сервере
  sync_seconds: 15
```
Агент трогает **только свои** таблицы, цепочки и правила, чужие правила брандмауэра не меняются.
Программы запускаются без оболочки, а адреса проходят строгую проверку, поэтому подставить в команду что-то лишнее нельзя.
`sentinel-agent test` проверяет связь и сразу применяет список, а `sentinel-agent firewall-clear` убирает все блокировки агента.
Состояние брандмауэра каждого сервера видно в панели: раздел «Серверы», столбец «Блокировки».

## Инциденты

Одна атака обычно даёт много алертов: сначала сканер, потом SQL-инъекция, потом перебор паролей. Сервер сам собирает
такие алерты в **инцидент** — одну карточку на атаку:
- алерты с одного IP попадают в один инцидент, пока атака не затихнет на `window` (по умолчанию час);
- если IP нет — группируются по пользователю на сервере, а если нет и пользователя — по правилу на сервере;
- важность инцидента — самая высокая из его алертов; название — главное правило и сколько ещё сработало.

В панели раздел **«Инциденты»**: список активных, фильтры «Мои» и «Без ответственного», поиск. В карточке:
- **«Взять себе»** — вы ответственный (имя берётся из имени ключа, с которым вы вошли);
- статусы «Открыт» → «В работе» → «Решён» или «Ложная тревога»; галочка «и алерты тоже» меняет статус всех алертов
  инцидента (по умолчанию включена);
- **заметки** — что выяснили и что сделали, видны всем;
- **«Объединить…»** — перенести алерты в другой инцидент (когда одна атака идёт с нескольких адресов);
- лента «Ход расследования»: алерты, заметки и действия людей по времени; сводка по атакующему IP и кнопка блокировки.

```yaml
incidents:
  window: 1h        # тишина, после которой новый алерт с того же адреса — уже новый инцидент (1m..30d)
```
Инциденты хранятся в `data/incidents.log` (журнал с CRC, как у алертов) и удаляются через `retention_days`
после последнего изменения.

## Выгрузка и отчёты

**Выгрузка.** Кнопка **«Выгрузить»** в разделах «События», «Алерты» и «Инциденты» скачивает то, что сейчас на экране
(с теми же фильтрами), до 100 000 строк:
- **CSV для Excel** — открывается двойным щелчком: кириллица не ломается, разделитель «;», время местное;
- **CSV** — обычный UTF-8 с запятыми, для других таблиц и скриптов;
- **JSON** / **NDJSON** — все поля, для программ.

Файл собирается на диске (`data/tmp/`) и отдаётся частями, поэтому даже миллион событий не занимает память сервера
(миллион событий — около 3 секунд). После отправки файл удаляется. Ячейки, похожие на формулы Excel
(`=…`, `+…`, `@…`), записываются с апострофом — чужая «формула» из лога не выполнится при открытии.
Через API можно выгрузить до 1 000 000 строк: `GET /api/v1/export/events?format=excel&src_ip=1.2.3.4&limit=1000000`.

**Отчёт за период** — раздел **«Отчёт»**: 7 или 30 дней, прошлая неделя, месяц или свои даты. В отчёте:
- сколько было событий, алертов и новых инцидентов, сколько открыто сейчас;
- алерты по дням и по важности;
- главные инциденты и как их разобрали: сколько решено, сколько ложных тревог, обычное время до закрытия;
- правила, которые срабатывали чаще всего, и доля ложных (у таких правил стоит подправить условия);
- самые активные адреса и страны, источники логов, блокировки.

Кнопка **«Печать / PDF»** открывает печать браузера: страница печатается в светлом виде, «Сохранить как PDF» есть
в любом браузере.

**Еженедельное письмо** с тем же отчётом (HTML + текст) уходит через почту из раздела `notify.email`:
```yaml
reports:
  weekly:
    day: monday        # monday … sunday или понедельник … воскресенье
    time: "09:00"      # местное время сервера
    to: [boss@example.com]   # по умолчанию — адреса из notify.email.to
```
Письмо за прошедшие 7 дней. Если почта была недоступна, отправка повторяется через 30 минут; если сервер был выключен
в момент отправки — письмо уйдёт после запуска. Администратор может отправить отчёт сразу кнопкой
«Отправить на почту» на странице отчёта.

## Страна, сеть и чёрные списки адресов

**База стран и сетей** — своя, без сторонних библиотек: отсортированные диапазоны и двоичный поиск
(IPv4 и IPv6, ~0.4 мкс на адрес). Данные — открытые CSV-файлы, например DB-IP Lite (лицензия CC BY 4.0):
```bash
# https://db-ip.com/db/lite.php (или зеркало: github.com/sapics/ip-location-db)
./build/sentinel-server geo-import dbip-country-ipv4.csv dbip-country-ipv6.csv dbip-asn-ipv4.csv
./build/sentinel-server geo-lookup 8.8.8.8          # 8.8.8.8: US, AS15169 Google LLC
```
Поддерживаются файлы стран (`начало,конец,страна`), сетей (`начало,конец,ASN,владелец`), городов DB-IP City Lite
и `iptoasn` (TSV). Импорт 1 млн диапазонов занимает около секунды; работающий сервер подхватывает новую базу сам.

**Чёрные списки** — сервер скачивает их сам (своим HTTP-клиентом) и обновляет по расписанию. Копия хранится
в `data/threat/`, поэтому после перезапуска списки работают и без интернета.
```yaml
threat_intel:
  refresh: 6h
  lists:
    - name: firehol_level1
      url: https://raw.githubusercontent.com/firehol/blocklist-ipsets/master/firehol_level1.netset
    - name: spamhaus_drop
      url: https://www.spamhaus.org/drop/drop.txt
    - name: tor_exit
      url: https://check.torproject.org/torbulkexitlist
    - name: my_list
      file: /etc/sentinel/bad-ips.txt     # свой список: адрес или подсеть в строке
```

**Что получают события.** Каждое событие с внешнего IP при приёме получает поля `geo.country`, `geo.city`,
`geo.asn`, `geo.org`, а если адрес есть в списках — `ti.listed: true` и `ti.lists`. По ним можно искать
(`/events?geo.country=CN`) и писать правила:
```yaml
where:
  geo.country: [CN, KP]
  ti.listed: 'true'
```
Готовое правило `TI-LISTED-001` «Обращение с адреса из чёрного списка» работает, как только подключены списки.
Внутренние адреса (10.x, 192.168.x и т. п.) не обогащаются.

**Карточка IP** в панели (`/ip/1.2.3.4`, любой IP в панели — ссылка на неё): страна и сеть, в каких списках адрес,
заблокирован ли, активность по дням, что он открывал на сайте, под какими логинами входил, на каких серверах
появлялся, какие правила сработали. Там же кнопка «Заблокировать». На обзоре — блок «Страны».

## Отправка логов

Строки логов как есть: формат определяется автоматически.
```bash
curl -X POST http://127.0.0.1:8080/api/v1/ingest \
  -H "Authorization: Bearer <ключ>" \
  -H "X-Sentinel-Host: web-01" \
  --data-binary @/var/log/nginx/access.log
```

Необязательные заголовки:
- `X-Sentinel-Source`: имя источника;
- `X-Sentinel-Format`: `nginx`, `syslog`, `json` или `kv`, если автоопределение не подходит;
- `X-Sentinel-TZ`: смещение часового пояса в минутах для логов без зоны (syslog), например `180` для Москвы.

События из своего приложения отправляются в JSON:
```bash
curl -X POST http://127.0.0.1:8080/api/v1/ingest -H "Authorization: Bearer <ключ>" \
  -H "Content-Type: application/json" \
  -d '[{"type":"auth","action":"login","outcome":"failure","user":"ivan","src_ip":"1.2.3.4"}]'
```

## Правила

Каждое правило — это YAML-файл в `rules/`. Изменения подхватываются без перезапуска: и сделанные в панели,
и правка файлов вручную.

```yaml
id: WEB-SQLI-001
name: SQL-инъекция в запросе
severity: critical            # info | low | medium | high | critical
type: match                   # match | threshold | sequence
where:
  type: web
field: http.path
transform: [unescape, url_decode, html_decode, remove_sql_comments, compress_space, lowercase]
patterns:
  - 'union(\s+(all|distinct))?\s+select[\s(*@0-9]'
message: 'SQL-инъекция с {src_ip}: {http.path}'
tests:
  match:     ['<строка лога, на которую правило ДОЛЖНО сработать>']
  no_match:  ['<строка, на которую НЕ должно>']
```

- `threshold`: `threshold: 5`, `window: 300`, `group_by: [src_ip]`. С `distinct: user` считаются **разные** значения поля (так ловится подбор логинов).
- `sequence`: шаги по порядку в пределах `within` секунд. Шаг — это либо срабатывание правила (`rule: AUTH-BRUTE-001`), либо событие (`where: {...}`).
- Повторы одного алерта подавляются на время `cooldown`, а число подавленных повторов попадает в следующий алерт.
- Условия в `where`: значение, список значений, `{regex: ...}`, `{not: ...}`, `{contains: ...}`, `{gte: 400}`, `{exists: true}`.
- Регулярные выражения пишите в 'одинарных кавычках', тогда обратную косую черту не нужно удваивать.

`sentinel-server test-rules` прогоняет все примеры из `tests:`. Пишите туда реальные ложные срабатывания, тогда они не вернутся.

### Редактор правил в панели

Раздел «Правила» → правило (или «Новое правило» с шаблонами «Одно событие», «Порог», «Цепочка»):
- **проверка на лету**: через секунду после правки видно, всё ли в порядке (YAML, регулярные выражения, ссылки
  цепочек, встроенные примеры `tests`); строка с ошибкой YAML подсвечивается;
- **«На строках»**: вставьте строки логов, и правило пройдёт по ним, как по живому потоку. Видно, какие строки дали
  алерт, а нажатие на строку показывает поля события, по которым работает правило;
- **«На событиях»**: правило пройдёт по уже сохранённым событиям за час, сутки, 3 дня или неделю и покажет, сколько
  алертов оно дало бы (и примерно сколько в сутки). Так видно заранее, не будет ли оно «шуметь»;
- **сохранение** (только администратор, Ctrl+S): правило попадает на диск только после полной проверки, включая
  все примеры из `tests`, и сразу начинает работать. Нельзя выключить или удалить правило, на которое ссылается
  цепочка;
- **версии**: каждое изменение сохраняется в `data/rules-history/` (кто и когда менял, последние 50 версий);
  прошлую версию можно открыть в редакторе и сохранить обратно;
- комментарии и оформление файла сохраняются, а включение и выключение меняет только строку `enabled:`.

Роли: смотреть правила может любой вошедший; проверять — `analyst` и `admin`; сохранять, включать и удалять — `admin`.

## Скорость (замер `sentinel-bench`, 500 000 строк)

| Этап | Ваш компьютер (VM, 4 ядра) | Облачная машина (2 ядра) |
|---|---|---|
| Разбор логов, 1 поток | ~2.3 млн строк/с (~355 МБ/с) | ~1 млн строк/с |
| Обнаружение, 15 правил, 1 поток | ~1 млн событий/с | ~380 тыс. событий/с |
| Обнаружение, 3 потока по IP + 1 общий | ~2.5 млн событий/с | — |
| Запись на диск со сжатием (~6.3 раза) | ~3.4 млн событий/с (сжатие в 2 потоках) | ~530 тыс. событий/с |
| Поиск IP, которого нет в данных | ~0 мс: блоки отсекаются bloom-фильтрами | ~0 мс |
| Сквозной приём по HTTP (разбор + обнаружение + запись) | **~1.08 млн событий/с** (было ~600 тыс.) | ~285 тыс. событий/с |

Потоки подбираются сами по числу ядер; задать вручную можно в `sentinel.yaml`:
```yaml
detect_threads: auto   # потоков обнаружения (события делятся между ними по IP источника)
store_threads: auto    # потоков сжатия при записи на диск
```
**Как обнаружение работает в нескольких потоках.** Все события одного IP всегда попадают в один и тот же поток,
поэтому подсчёт вроде «5 неудачных входов за 5 минут с одного адреса» остаётся точным. Правила, которые считают
по другим полям (например, `group_by: [user, host]`), проверяет отдельный общий поток, а цепочки всегда работают
вместе с правилами, на которые ссылаются. Тесты проверяют, что в 1, 2, 3 и 7 потоках получаются ровно те же
алерты, что и в одном. На 1–2 ядрах сервер работает в одном потоке обнаружения: так быстрее.

## Хранение данных

```
data/
  events/seg-<время>-<номер>.sntl   события: новый сегмент каждый час
  alerts.log                         алерты и смены статусов
  incidents.log                      инциденты: алерты, статусы, ответственные, заметки
  reports.json                       когда ушло последнее еженедельное письмо

  blocks.json                        заблокированные адреса

  agents.json                        список подключённых серверов
  rules-history/<файл>/              версии правил, изменённых из панели
  geo/geo.bin                        база стран и сетей (geo-import)

```
- Каждый блок защищён CRC. Если питание пропало во время записи, при старте недописанный хвост отрезается, а остальные данные сохраняются.
- Старые сегменты удаляются автоматически через `retention_days`.

## Что дальше

Этап 6 «Расследование» завершён. Возможные следующие шаги: корреляция между серверами (одна атака на несколько
машин), роли с доступом только к своим серверам, долгое хранение со сжатием старых сегментов, кластер из нескольких
серверов SentinelCore.

Ограничения: `Transfer-Encoding: chunked` не поддерживается (агент отправляет `Content-Length`).
Сборка и тесты на macOS (Apple Silicon и Intel) и Linux идут на GitHub Actions при каждом изменении.
